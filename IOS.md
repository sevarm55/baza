# Տետր для iOS — план

Документ отвечает на два вопроса: что придётся построить, кроме самого
приложения, и в каком порядке. Оценки даны для одного разработчика.

---

## 1. Что уже есть

Разбор текущего продукта — от него зависит всё остальное.

**Модель данных** (`lib/db/schema.ts`) — 8 таблиц, мультитенантность через
`tenant_id` на каждой. Три решения, которые приложение обязано уважать:

| Решение | Где | Почему это важно для iOS |
|---|---|---|
| Цена, название услуги и процент пишутся **снимком** в заказ | `orders.serviceName/price/staffPercent` | Приложение не пересчитывает историю. Прайс поменялся — старые записи прежние |
| `clientRef` уникален по тенанту | `orders_client_ref_uniq` | Готовая идемпотентность: досылка из офлайна не создаёт вторую машину |
| Мягкая отмена | `orders.canceledAt` | Отменённое остаётся в истории; приложение не удаляет |

**Деньги** — в минимальных единицах (драмах), целыми числами. Форматирование
на клиенте. Валюта, часовой пояс и термины бизнеса (`clientIdLabel`,
`clientIdType`, `unitOne`, `staffRole`) приходят из тенанта.

**Операции** — 16 Server Actions (`app/actions.ts`) и 16 запросов чтения
(`lib/queries.ts`). Ядро записи — `createOrder` в `lib/orders.ts`: одна
транзакция, upsert клиента, списание абонемента условным UPDATE, аудит.

**Вход** — телефон в E.164 плюс PIN из 4 цифр, `scrypt`. Сессия — JWT HS256
(`jose`) в httpOnly-cookie на 30 дней.

**Подписка** — `trial | active | expired | blocked` с раздельными `canRead`
и `canWrite`: просрочка закрывает запись, но не чтение.

**Офлайн** — очередь в `localStorage` (`lib/offline.ts`) с `ref` на каждую
запись. Логика ровно та, что нужна нативному приложению.

## 2. Главный вывод: проект — это API, а не приложение

**HTTP-API у продукта нет.** Есть ровно два эндпоинта: выгрузка CSV
(`/owner/export`) и техническая заглушка `/session-ended`. Всё остальное —
Server Actions, которые вызываются из React и наружу не документированы.

Значит первая половина работы — серверная. Приложение без неё не начать.

Хорошая новость: бизнес-логику переписывать не нужно. `createOrder`,
`cancelOrder`, `currentAccess`, запросы из `lib/queries.ts` — всё это уже
чистые функции над базой. API — тонкий слой поверх них: разбор запроса,
проверка токена, вызов функции, сериализация. Плохо было бы наоборот.

---

## 3. Что даёт натив, чего не даёт нынешняя PWA

Продукт уже устанавливается на домашний экран, работает офлайн и имеет
сервис-воркер. Поэтому честный список выгод короткий — но в нём есть одна
позиция, которая одна оправдывает проект.

**Ради чего стоит:**

1. **Сканер номера камерой.** `VisionKit.DataScannerViewController` читает
   госномер с камеры. Для мойки это главный экран продукта: вместо ввода
   восьми символов мокрыми руками — навёл и снял. В вебе этого нет.
2. **Настоящая фоновая досылка.** `BGProcessingTask` отправляет очередь,
   когда приложение закрыто. Сервис-воркер так не умеет: он просыпается,
   только пока страница открыта.
3. **Push.** Владельцу — «смена закрыта, 47 000 ֏». Мойщику — «зарплата
   выплачена». Веб-push на iOS работает только для установленных PWA и
   ненадёжно.
4. **Face ID вместо PIN** после первого входа.
5. **App Store.** Для продажи по Армении наличие в сторе — аргумент доверия.

**Чего не даёт:** скорости (PWA уже быстрая), офлайна как такового (уже
есть), экономии — наоборот, добавляет второй клиент, который придётся
держать в согласии с первым при каждом изменении продукта.

**Что стоит денег:** аккаунт разработчика Apple — 99 $ в год; ревью при
каждом обновлении; для ревьюера нужен демо-аккаунт с данными.

## 4. API v1 — контракт ✅ реализовано

Всё ниже работает и покрыто проверками в `npm run smoke`. Обработчики —
обычные функции от `Request`, поэтому тесты зовут их напрямую, без
поднятого сервера.

Префикс `/api/v1`. JSON в обе стороны. Деньги — целые в минимальных
единицах. Время — ISO 8601 с зоной.

### Аутентификация

Cookie не годится: нативному клиенту нужен токен, который можно отозвать.

```
POST /auth/login     {phone, pin, deviceId, deviceName} → {access, refresh, expiresIn}
POST /auth/refresh   {refresh}                          → {access, refresh}
POST /auth/logout    {refresh}                          → 204
GET  /auth/devices                                      → список устройств
DELETE /auth/devices/{id}                               → отозвать
```

`access` — JWT на 15 минут, тот же секрет и та же проверка, что сейчас.
`refresh` — случайная строка в новой таблице `sessions` (id, tenant_id,
user_id, device_id, token_hash, created_at, last_seen_at, revoked_at).
Отзыв устройства работает мгновенно, чего нынешняя схема не умеет вовсе.

### Один вызов на старте

```
GET /bootstrap → {
  tenant: {name, currency, timezone, clientIdLabel, clientIdType, unitOne, staffRole},
  me:     {id, name, role, percent},
  access: {state, daysLeft, canRead, canWrite},
  services: [{id, name, price, sort}],
  syncedAt
}
```

Всё, что нужно экрану записи, одним запросом. Приложение кэширует ответ и
работает из кэша, пока связи нет.

### Экран мойщика

```
POST /orders                  {ref, clientKey, serviceId, payment, passId?, note?}
GET  /shift?from=             → {count, revenue, earned, percent, recent[]}
GET  /clients/lookup?key=     → {known?: {visits, lastSeenAt, total}, passes[]}
POST /orders/{id}/cancel
```

`POST /orders` — идемпотентный по `ref`. Повторная отправка возвращает
**200** и ту же запись, первая — **201**. Это уже реализовано в
`createOrder`, эндпоинту остаётся правильно отдать код.

### Кабинет владельца

```
GET  /summary?period=today|7|30   → {stats, series, split, feed}
GET  /payroll                     → {due[], payouts[]}
POST /payouts                     {staffId}
GET  /clients
```

Сводка отдаётся одним ответом, а не четырьмя. В вебе четыре запроса
уходят параллельно внутри одного рендера, и там это правильно; на
мобильной сети четыре round-trip складываются в паузу, а часть ещё и
обрывается.

Сумма выплаты НЕ принимается от клиента — только `staffId`. Считает
сервер, иначе подделанный запрос запишет в историю выплат любую цифру.
Логика вынесена в `lib/payroll.ts` и общая с кабинетом: расчёт с
человеком — не то место, где можно держать две копии.

Правка услуг и сотрудников через API пока не открыта: в приложении это
редкое действие, а веб для него есть.

### Ошибки

Машиночитаемые коды, а не тексты — приложение переводит само:

```json
{"error": "PASS_UNAVAILABLE", "message": "..."}
```

Коды уже существуют как классы ошибок: `SERVICE_NOT_FOUND`,
`STAFF_NOT_FOUND`, `PASS_UNAVAILABLE`, `DUPLICATE_REF`,
`SUBSCRIPTION_EXPIRED`. Их надо просто вынести в общий перечень.

## 5. Безопасность ✅ закрыто

Три дыры, из-за которых API нельзя было открывать. Все закрыты до того,
как появился первый эндпоинт.

**1. Ограничение попыток входа** — `lib/login-guard.ts`. Считаем неудачи
по номеру и по адресу: первое защищает человека от подбора PIN, второе —
от перебора номеров подряд. Счётчик спрашивается ДО сверки, чтобы при
переборе не выполнялся ни scrypt, ни сама проверка. Задержка растёт
1 → 2 → 5 → 15 → 60 минут, удачный вход её обнуляет. Таблица, а не память
процесса: память чистится деплоем, то есть когда защита нужнее всего.

**2. Отзыв токена** — таблица `sessions`, в JWT лежит `sid`. Строка в базе
решает, жив токен или нет; отзыв мгновенный. Проверка живёт в
`requireSession`, а не в `getSession`: последний зовут лендинг и окно
входа, и тянуть ради них базу нельзя.

**3. Поколение токенов** — `users.tokenVersion`. «Выйти везде» и смена PIN
гасят все выданные разом.

**4. Транспорт.** ATS требует HTTPS — он уже есть (Caddy, Let's Encrypt).
Пиннинг сертификата не нужен: домен на duckdns, ротация сломает приложение.

Отдельно про refresh: он **ротируется** при каждом обмене. Украденный
токен работает ровно один раз — как только настоящий владелец обновится
следующим, чужой перестанет подходить.

## 6. Приложение

**Стек.** Swift 5.9+, SwiftUI, Swift Concurrency (`async/await`, `actor`
для очереди). Сеть — `URLSession`, без сторонних библиотек: запросов
полтора десятка. Токены — Keychain. Локальное хранилище — **GRDB.swift**
(очередь, кэш услуг и клиентов). Не SwiftData: она требует iOS 17.

**Минимальная версия — iOS 16.** Аудитория продукта — мойщики и владельцы
малого бизнеса в Армении, телефоны там живут долго. iOS 17 отрезает
заметную долю.

**Архитектура.** MVVM: `APIClient` (протокол, чтобы подменять в тестах) →
`Repository` (решает, идти в сеть или в кэш) → `ViewModel` → SwiftUI-вид.
Локализация с первого дня: армянский основной, строки берутся из того же
словаря, что и веб (`lib/i18n/hy.ts` → экспорт в `.xcstrings`), иначе
продукт начнёт говорить двумя разными голосами.

**Экраны фазы 1 (мойщик):**

1. **Вход** — телефон, затем PIN. После первого входа — Face ID.
2. **Смена** — заработок крупно, число машин, кнопка «+ машина» во весь
   низ экрана, лента последних записей, значок несинхронизированных.
3. **Запись** — три шага: клиент → услуга → оплата. На первом шаге
   кнопка сканера.
4. **Готово** — подтверждение и возврат на смену.

**Офлайн.** Порядок ровно как в вебе, но надёжнее: запись сразу в GRDB со
своим `ref`, экран показывает успех немедленно, отправка — отдельная
задача. `BGProcessingTask` досылает очередь в фоне, `NWPathMonitor` —
сразу при появлении связи. Сервер по `ref` отличит повтор от новой машины.

**Фаза 2 (владелец)** — сводка за период, график, разбивка по оплатам,
зарплаты с историей выплат, база клиентов. Отдельная вкладка, тот же
логин: роль приходит в `/bootstrap`.

## 8. Риски

**Два клиента вместо одного.** Каждое изменение продукта теперь нужно
делать дважды. Смягчается тем, что API один и бизнес-логика на сервере, —
но экраны придётся держать в согласии руками.

**Ревью Apple.** Инструмент для бизнеса проходит спокойно, но нужен
демо-аккаунт с данными, иначе отклонят на первом же круге.

**Сканер номера.** `DataScannerViewController` читает текст, а не
госномера: армянский формат `12 AB 345` придётся доводить постобработкой
и обязательно оставить ручной ввод рядом.

**Часовой пояс.** Смена и «сегодня» считаются в зоне тенанта
(`Asia/Yerevan`), а телефон может быть в другой. Все границы суток —
только с сервера, приложение своё «сегодня» не вычисляет.

## 9. Что нужно решить до старта

1. **Объём первой версии** — только мойщик или сразу оба кабинета.
2. **Судьба веба** — остаётся полноценным продуктом или становится только
   кабинетом владельца, а запись уходит в приложение.
3. **Аккаунт Apple** — на кого оформляется: организация или частное лицо.
   Организации нужен D-U-N-S, это две-три недели само по себе.
4. **Android** — если он планируется, API проектируется один раз, и это
   аргумент не экономить на фазе 0.
