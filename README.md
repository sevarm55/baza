# Tetr · Տետր

Тетрадь, которая считает сама.

Учёт для сервисного бизнеса: одно ядро, разные ниши.

Автомойка, стоматология, автосервис, барбершоп, клининг, ветклиника — внутри
устроены одинаково: приходит клиент, ему делают услугу, исполнитель получает
процент, владелец считает деньги. Различаются только слова, услуги и ставки,
а это данные, а не код.

При регистрации бизнес выбирает свой тип и получает **готовую систему**
со своими услугами и терминами, а не пустой конструктор.

## Что умеет

**Сотрудник** — запись за три касания: идентификатор клиента → услуга → оплата.
Видит свой заработок в реальном времени, узнаёт постоянных клиентов при вводе,
работает без интернета.

**Владелец** — выручка за период, выработка по каждому, расчёт зарплат
с историей выплат, база клиентов с детектом пропавших, абонементы,
редактор прайса, выгрузка в Excel.

## Разработка

```bash
npm install
npm run dev
```

База поднимается сама: PGlite — настоящий Postgres 16 в WASM, файлы в `.data/`.
Ставить ничего не нужно.

```bash
npm run smoke       # проверка слоя данных на чистой базе в памяти
npm run typecheck
npm run icons       # пересобрать иконки приложения
```

Подписка на первых клиентах отмечается вручную:

```bash
npm run activate -- +37477111222 3
```

```bash
npm run trial -- +37477111222 7
```

Сервер при этом должен быть остановлен: локальная база не пускает к себе
два процесса сразу.

## Устройство

```
lib/niches.ts       конфиги ниш — единственное место, где они существуют
lib/db/schema.ts    8 таблиц, tenant_id на каждой
lib/orders.ts       ядро: создание и отмена записи
lib/queries.ts      все чтения, всегда со scope по бизнесу
lib/passes.ts       абонементы
lib/subscription.ts состояние подписки
lib/offline.ts      очередь записей, сделанных без связи
```

Три правила, на которых всё держится:

1. **Цена, услуга и процент пишутся снимком в каждый заказ.** Владелец меняет
   прайс — вчерашняя выручка и зарплаты остаются прежними.
2. **Ядро не знает про ниши.** Конфиг используется один раз, при регистрации.
3. **Каждое действие само проверяет права.** Server Action — открытый
   POST-эндпоинт, а не внутренняя функция.

## Деплой

Приложение само выбирает базу по переменной окружения:

| | |
|---|---|
| `DATABASE_URL` задан | настоящий Postgres (сервер) |
| не задан | PGlite, локальные файлы в `.data/` |

Диалект один и тот же, поэтому схема, миграции и запросы не меняются.

`npm run dev` при этом на чужой сервер не пойдёт: строка `.env.local`
живёт вечно, а вставляют её однажды, чтобы «посмотреть, как там на самом
деле», — и дальше каждая проверка идёт по живым мойкам. Разработка
работает только со своей базой, а если чужая нужна осознанно:

```bash
TETR_ALLOW_REMOTE_DB=1 npm run dev
```

Сборка, сервер и скрипты (миграции, активация подписки) под это правило
не попадают — им боевая база и нужна.

То же самое у приложения: отладочная сборка ходит на `localhost:3100`,
магазинная — на боевой сервер, и переменными это не подменяется. Адрес
для отладки лежит в схеме Xcode (`ios/project.yml`, переменная
`TETR_API`); значение `prod` означает осознанный выход в бой, а
`http://192.168.1.5:3100/api/v1/` — телефон в одной сети с компьютером.

Переменные окружения на сервере:

```
DATABASE_URL=postgres://...
SESSION_SECRET=<случайная строка от 32 символов>

# Отправка SMS. Без неё регистрация не проходит: номер подтверждается
# кодом, и подтвердить его нечем.
#
# Задают ОДИН из вариантов. Именные проверяются раньше общего шаблона.
#
# D7 Networks — укладывается в общий шаблон, своего кода не требует:
SMS_ENDPOINT=https://api.d7networks.com/messages/v1/send
SMS_TOKEN=<access token из кабинета D7>
# Общий отправитель оператора — пока имя `Tetrin` не одобрено
# операторами Армении. Регистрация идёт три-четыре недели, подавать
# заявку надо заранее; после одобрения здесь меняется одно слово.
SMS_SENDER=SignOTP
SMS_BODY={"messages":[{"channel":"sms","recipients":["{to}"],"content":"{text}","msg_type":"text","data_coding":"unicode"}],"message_globals":{"originator":"{sender}"}}
# `unicode`, а не `auto`: армянские буквы не помещаются в GSM-7, и при
# автоопределении оператор молча заменяет их вопросительными знаками.
# Проверено вживую — приходит «????» вместо текста.
#
# Vonage:
# VONAGE_API_KEY=<из дашборда>
# VONAGE_API_SECRET=<оттуда же>
# VONAGE_FROM=Tetrin
#
# Twilio:
# TWILIO_ACCOUNT_SID=ACxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
# TWILIO_AUTH_TOKEN=<из консоли Twilio>
# TWILIO_FROM=Tetrin
#
# Кто угодно ещё, у кого отправка — это POST с JSON. `SMS_AUTH_SCHEME`
# нужен там, где перед секретом стоит не `Bearer`: у Infobip это `App`.
# SMS_AUTH_SCHEME=App
#
# У Vonage и Twilio то же самое: пока имя не одобрено, вместо `Tetrin`
# ставят купленный номер или общего отправителя оператора.

# Необязательные, но желательные: разные секреты для разных задач.
# Не заданы — выводятся из SESSION_SECRET с собственной меткой
# назначения, то есть никогда с ним не совпадают.
OTP_SECRET=<случайная строка>
DEVICE_SECRET=<случайная строка>

# Домен для кода из SMS (Origin-bound One-Time Codes) и для списка
# разрешённых источников. Второй нужен, только если наружный хост не
# совпадает с внутренним — за обратным прокси или на staging.
PUBLIC_DOMAIN=tetrin.pro
PUBLIC_ORIGIN=https://tetrin.pro
ALLOWED_ORIGINS=https://tetrin.pro
```

Без `SESSION_SECRET` приложение в продакшене не запустится специально:
иначе сессии подписывались бы общеизвестным дефолтом, и подделать cookie
владельца смог бы кто угодно.

Без провайдера в продакшене отправка кода честно отвечает отказом и
пишет об этом в лог, а не печатает код: неотправленная SMS обязана быть
видимой ошибкой. Локально код печатается в консоль сервера — этого
хватает для работы.

Текст кода умещается в одну SMS (53 символа из 70). Семьдесят, а не сто
шестьдесят, потому что армянские буквы кодируются UCS-2. Длинный
`PUBLIC_DOMAIN` может вывести за предел — тогда каждое сообщение станет
двумя, и об этом предупредит строка в логе.

Миграции на сервере применяются отдельным шагом, а не при старте —
иначе параллельные экземпляры мигрировали бы одну базу наперегонки:

```bash
DATABASE_URL=... npm run db:migrate
```

## Тестовый стенд

`test.tetrin.pro` — та же сборка, что и бой, на отдельном домене, с
отдельной базой и без единого канала наружу. Новое едет сначала туда,
и только проверенное попадает в `main`.

Стенд собирается тем же образом и с тем же `NODE_ENV=production`. Это
не формальность: стенд, собранный иначе, проверяет не то приложение,
которое поедет к клиентам. Всё отличие включает одна переменная —
`STAGING=1` (см. [lib/staging.ts](lib/staging.ts)):

| | |
|---|---|
| SMS | не отправляются, код подтверждения печатается в лог |
| Поисковики | `robots.txt` запрещает индексацию целиком |
| Интерфейс | рамка по периметру окна и метка в имени вкладки |

Пуши, задачи по расписанию и телефоны платформы выключены отдельно, в
самом `docker-compose.test.yml`, и пустыми значениями, а не отсутствием
строки: даже боевой `.env`, случайно скопированный на стенд, их не
включит.

### Как поднять в первый раз

Три шага, из них два разовые.

**1. DNS.** В панели reg.ru запись `A` для `test` на IP сервера. Проверить:

```bash
dig +short A test.tetrin.pro
```

**2. Caddy.** Порты 80/443 держит Caddy соседа, поэтому стенд, как и бой,
наружу не торчит ни одним портом: его пускают по имени внутри сети. В
`/opt/giperstroy/infra/prod/Caddyfile` рядом с блоком `tetrin.pro`:

```
test.tetrin.pro {
	encode zstd gzip
	reverse_proxy bazis-test-web:3000
}
```

Сертификат Caddy получит сам. Перечитать конфиг без простоя соседа:

```bash
docker exec giperstroy-caddy caddy reload --config /etc/caddy/Caddyfile
```

**3. Каталог и секреты.** Стенд живёт в `/opt/bazis-test`, отдельно от
боевого `/opt/bazis`: один рабочий каталог не может быть на двух ветках
сразу.

```bash
git clone <репозиторий> /opt/bazis-test
cd /opt/bazis-test && git checkout test
```

Дальше `infra/.env.test`, и секреты в нём НОВЫЕ, не боевые:

```bash
POSTGRES_PASSWORD=<openssl rand -hex 24>
SESSION_SECRET=<openssl rand -hex 32>
ADMIN_LOGIN=<логин для /admin на стенде>
ADMIN_PASSWORD_HASH=<npx tsx scripts/admin-password.ts>
```

Общий с боем `SESSION_SECRET` означал бы, что cookie, выписанная
стендом, открывает кабинет на `tetrin.pro`. Скрипт деплоя это проверяет
и отказывается работать при совпадении.

### Как выкатывать

```bash
ssh contabo "cd /opt/bazis-test && bash infra/deploy-test.sh"
```

По умолчанию ветка `test`; аргументом можно передать любую другую.
Скрипт делает `reset --hard` на ветку: стенд ничего своего не хранит и
обязан быть точной копией того, что проверяется.

Дальше обычный путь правки: `test` → проверка на стенде → слияние в
`main` → `bash infra/deploy.sh`.

### Как войти на стенд

База стенда своя и пустая, SMS не отправляются. Код подтверждения
печатается в лог контейнера:

```bash
ssh contabo "docker logs -f bazis-test-web | grep 'sms:dev'"
```

### Чего на стенде делать нельзя

Заносить в `infra/.env.test` боевые ключи APNS, FCM или SMS. База стенда
пустая, но токен устройства в неё оставит НАСТОЯЩИЙ телефон того, кто
зайдёт со своего, и следующая проверка уведомлений разбудит его
сообщением о смене, которой не было.

Обратное тоже проверяется автоматически: боевой `infra/deploy.sh`
отказывается выкатываться, если увидит `STAGING` в своём `.env`. В бою
эта переменная означала бы, что зарегистрироваться не может никто, а
сайт при этом выглядит работающим.

## Шрифты

| Где | Шрифт | Откуда |
|---|---|---|
| Интерфейс | Mardoto | `app/fonts/`, Apache 2.0 |
| Марка и заголовок витрины, латиница и кириллица | Unbounded Black | `app/fonts/` |
| То же, армянский | Montserrat Armenian Black | `app/fonts/`, fonter.am |

[Mardoto](https://github.com/vahanhovh/mardoto) лежит в проекте, потому что его нет
в Google Fonts. Текст лицензии — `app/fonts/MARDOTO-LICENSE.txt`.

Крупный набор идёт тремя файлами, потому что ни одна гарнитура не покрывает
все три письменности: в Unbounded нет армянских глифов вовсе. Условия
Montserrat Armenian — `app/fonts/MONTSERRAT-ARMENIAN-LICENSE.txt`.
